# 完整教學案例｜客戶產品需求整理

**性質：模擬案例，所有對話及回饋均為教學設計。未進行真實企業實測。**

## 一、原始輸入

主管說：「需求交到產品部後常被退回，我想用 AI 自動整理。」  
業務紀錄：「客戶想做一款隨身保溫杯，首批希望 500 個，下個月活動要用，希望價格不要太高。」  
資深同事說：「我會先問使用場景、容量、預算與收貨日期，再請產品部評估。」

已知：客戶想做保溫杯、期望數量 500 個、提到活動用途。  
未知：容量、材質要求、預算範圍、絕對收貨日期與供應可行性。  
推論：資訊缺漏可能造成退件，但尚無退件紀錄可證明它是主要原因。

## 二、用 M1–M4 拆解

| 機制 | 判讀 | 下一步 |
|---|---|---|
| M1 | 可能卡在原始資料不足，也可能卡在產品部排程 | 先查退件原因，確認缺漏是否已出現在原始紀錄 |
| M2 | 關鍵確認值得保留，重複抄寫未必必要 | 必填項對應用途；已有答案不重問 |
| M3 | 資深同事的提問可整理成新人清單 | 每項寫明用途與缺漏時的追問 |
| M4 | 退件原因可作修訂依據 | 先觀察新人在哪裡卡住，再修改清單；改善效果尚未測量 |

## 三、完成的一頁蒸餾卡

| 欄位 | 示範內容 |
|---|---|
| 經驗與目標 | 將客戶的初步需求交接給產品部，讓產品部能判斷還缺什麼 |
| 觀察與判斷 | 原始紀錄沒有容量、預算與確切日期；先補問可能比直接整理更有幫助 |
| 一句原則 | 當資料不足以支持下一步評估時，先補問會改變判斷的資訊，避免把猜測當需求 |
| 流程 | ①標示已知與未知；②選出影響本次評估的缺漏；③詢問客戶並記錄答案；④交接已確認資訊與仍待確認處 |
| 案例 | 「下個月活動要用」需確認活動及收貨日期；不能直接承諾下個月可以交貨 |
| 適用與例外 | 適合初步需求交接；如已有核准規格，先核對版本，不要求客戶重新回答所有欄位 |
| 重用形式 | 新人需求確認清單，每項附「為何要問」 |
| 回饋與修訂 | 新人不知道「規格」要問什麼，改為「先問容量；不確定時請客戶提供參考產品」 |

## 四、模擬同儕檢查

新人：「如果客戶也不知道容量呢？」  
作者：「先請他提供參考產品或描述使用需求，再交產品部提出選項；不要自己填一個容量。」  
新人複述：「我先確認未知，不把我的猜測當成客戶指定規格。」

本示範呈現如何讓說明更可操作；未證明退件率、成交率或交接速度已改善。

## 五、示範評量

- 清楚：已知、未知與推論分開。
- 可教：模擬新人能說明缺容量時的下一步。
- 可重用：有流程、適用情境與例外。
